# 系统管理页（/admin）配置体验重构设计规格

> 目标：从「配置项集合」改为「围绕用户任务的配置流程」，Apple 式克制——一眼看懂「有什么 → 当前状态 → 是否已配置 → 下一步做什么」。

## 0. 验收标准（可检验）

1. **3 秒测试**：给一个没用过的人看主页面截图 3 秒，能说出「哪些还没配好」。
2. **每个模块回答三问**：这是什么（副标题）→ 现在什么状态（右侧值）→ 下一步做什么（引导语）。
3. **状态词全系统统一**：只用 `已配置 / 未配置 / 部分配置 / 需注意` 四种。
4. **任何配置任务 ≤ 3 次点击**：状态卡 → Drawer → 字段。
5. **移动端**：Drawer 变全屏页（iOS push 模式），不是窄抽屉。

## 1. 信息架构：内容操作 + 配置中心（两大心智区）

> 分组依据：**操作 vs 配置** 是第一维度，配置内部再按 **配置 / 调优 / 运维** 分层。
> - 操作类（媒体库扫描、文件管理）= 围绕媒体文件的**日常任务**，走侧边栏直达，不进配置页。
> - 配置类 = 一次性设置，集中在 /admin 配置中心。
> 这样 /admin 是**纯配置心智**，操作类不混入。

```
内容操作（侧边栏，非配置，日常任务）
├─ 媒体库管理   数据源：路径 / 扫描 / 进度 / 归类规则   ← 从 admin library 移出
└─ 文件管理     浏览 / 批量刮削 / 改名 / 移动 / 导入     ← 现有 /files

配置中心 /admin（重构后）
├─ ① 概览（默认落地页）          状态卡列表（按配置分层分组）+ 下一步引导 + 运行状态摘要
│
├─ ── 媒体设置（配置重心，小白最先接触）──
│   ├─ 元数据刮削   传统识别：TMDb Key / 豆瓣 Cookie / 代理
│   └─ AI 服务      智能识别：托管模式 / Key / 模型 / 功能开关
│
├─ ── 播放与存储设置（高级配置，默认即用）──
│   ├─ 播放与转码   GPU / 直连 / 路径 / 自动转码
│   └─ 存储         WebDAV / Alist / S3
│
├─ ── 用户与系统设置（运维操作，非配置）──
│   ├─ 用户管理
│   └─ 日志
│
└─ /profile 个人中心（保持不变）  用户名 / 密码 / API Key / 登出
```

**为什么这样分**：
- **媒体库管理是操作不是配置**：扫描按钮、重建索引、进度条都是日常操作；路径/类型只是前置配置。它和文件管理是连续工作流（媒体库源 → 扫描 → 文件管理结果），同属「内容操作」区。
- **① 媒体设置** = 「配置一次」的关键工作流（配 TMDb → 配 AI），新用户在此完成"内容被正确识别"的配置。
- **② 播放与存储设置** = 「默认即用」的高级调优，配一次后基本不动，动的人是专业用户。
- **③ 用户与系统设置** = 「运维操作」而非配置（监控 / 排查 / 权限），不属于"设置"心智。
- 不把存储并入媒体设置：它和播放转码同属"运行时行为"心智。
- 不把 AI 拆成独立组：它作用于内容识别、与元数据强相关，单独一组只 1 项太孤。

**拆解动作**（相对现状）：
| 现状 | 去向 |
|---|---|
| dashboard 实时进度 / 系统状态 | 概览页底部次要区块「运行状态」 |
| dashboard 系统设置 8 项 | 播放与转码 Drawer（配置中心 ②） |
| dashboard 清空数据 | 用户与系统设置，沉底红区 |
| library tab TMDb / 豆瓣 | 元数据刮削 Drawer（配置中心 ①） |
| library tab 媒体库（LibraryManager） | 移出 admin → 内容操作区「媒体库管理」（落地方式见 §8 待定 A/B/C） |
| AITab 统计/缓存/测试 | AI Drawer 内折叠「更多」 |
| StorageTab 保留 | 存储 Drawer（现有卡片切换模式就是对的，保留） |

## 2. 主页面布局（概览）

```
┌──────────────────────────────────────────────────────┐
│ 系统管理                          [🔍 搜索] [●实时]    │
├──────────────────────────────────────────────────────┤
│ ▸ 下一步：配置 TMDb API Key → 自动获取海报简介评分      │
├──────────────────────────────────────────────────────┤
│ 媒体设置（配置重心）                                  │
│ ┌─ 元数据刮削 ─┐ ┌─ AI 服务 ──┐                      │
│ │ TMDb·未配置  │ │ 未配置      │  ›                  │
│ │ 豆瓣·未配置  │ │ 副标题一句话 │                     │
├──────────────────────────────────────────────────────┤
│ 播放与存储设置（高级配置，默认即用）                   │
│ ┌─ 播放与转码 ─┐ ┌─ 存储 ──────┐                     │
│ │ GPU·开      │ │ WebDAV·未配  │                     │
│ │ 副标题一句话  │ │ 副标题一句话  │                    │
├──────────────────────────────────────────────────────┤
│ 用户与系统设置（运维操作）                            │
│ ┌─ 用户 ─────┐ ┌─ 日志 ──────┐                      │
│ │ 3 用户      │ │ 查看/过滤    │                      │
├──────────────────────────────────────────────────────┤
│ 运行状态  CPU 8核 · 内存 2.1G · HW NVENC · v0.1.17    │
└──────────────────────────────────────────────────────┘
```

**布局规则**：
- 主页面 = 配置状态卡列表，**按 3 层分组**（组标题 + 组内 2-3 卡；媒体设置在前，运维沉底）。
- 分组是**视觉分层**（组标题分隔），不增加导航层级：点击任意子卡仍 2 次进 Drawer。
- 每卡：`icon + 标题 + 副标题(≤30字) + 右侧状态值 + chevron ›`。
- 状态值 = 文字徽章（绿=已配置 / 黄=部分配置 / 灰=未配置 / 红=需注意）+ 文字，**不只靠颜色**。
- 空状态 = 引导；非空状态 = 摘要。
- 危险操作永不进卡片列表，只在用户与系统设置页底部红区。
- 下一步引导按媒体设置组子项顺序推进：TMDb → AI。
- 媒体库管理 / 文件管理不走本页（操作类，侧边栏直达）；本页只聚合「配置状态」。

## 3. 状态模型（全系统唯一词汇表）

| 状态 | 徽章色 | 含义 | 示例 |
|---|---|---|---|
| 已配置 | 绿 | 关键项已配好 | TMDb Key 已保存 |
| 未配置 | 灰 | 尚未配置 | 豆瓣 Cookie 未配置 |
| 部分配置 | 黄 | 有一项配了 | TMDb✓ 豆瓣○ |
| 需注意 | 红 | 配置了但异常 | Key 失效 / 连接失败 / 配额用尽 |

## 4. 各 Drawer 规格（字段清单 + 默认/折叠分组 + 文案）

> 通用交互：Drawer 宽 480px（桌面）/ 全屏（移动）。就地保存、就地报错（不跳 toast 回主页面）。每模块标题下副标题 =「为什么需要它」。

### 内容操作 › 媒体库管理（操作区，非 Drawer）

> 媒体库管理是**操作不是配置**（扫描 / 重建索引 / 进度是日常任务），与文件管理同属「内容操作」区，侧边栏直达。落地方式见 §8（A/B/C 待定）。

**内容**（从 admin library tab 的 LibraryManager 原样迁移）：
- 媒体库列表（路径 / 类型 / 扫描时间 / 状态）
- 新增媒体库（路径 + 类型）+ 删除
- 扫描全部 / 单个 / 重建索引 + 扫描进度条（WebSocket 逻辑不动）
- 扫描归类规则（ClassificationTab，原样保留，折叠为高级区）

**引导**：空库时 → 「添加第一个媒体库路径」；有库未扫描 → 「扫描媒体库」。
**与文件管理的关系**：媒体库（源）→ 扫描 → 文件管理（结果），连续工作流，两入口相邻。

## 6. 实施步骤（增量，纯前端，无后端改动）

### 第一步：概览页骨架（低风险）
1. `AdminPage` 新增 `overview` 落地视图：6 张配置状态卡 + 下一步引导条 + 运行状态摘要（媒体库管理已移出）。
2. 引入 Drawer 组件（现有 `Dialog` 或新建 `Drawer`，宽 480 / 移动全屏）。
3. 把现有 dashboard 系统设置、library 配置整体**原样搬进**各自 Drawer，行为零改动。

### 第二步：拆模块 + 媒体库移出
4. library tab → 拆出「元数据刮削」Drawer（TMDb + 豆瓣 + 代理）；LibraryManager 按 §8 落地方式移入内容操作区。
5. dashboard 系统设置 → 迁入「播放与转码」Drawer；清空数据 → 用户与系统设置页。
6. AITab 统计/缓存/测试 → 折叠「更多」。

### 第三步：降噪 + 搜索
7. 各 Drawer 高级项折叠（默认 `<details>` 或手风琴）。
8. 搜索升级：索引全部配置项 + 显示状态 + 直达 Drawer（现在只搜 10 个写死跳转）。
9. 文案收敛（第 5 节表）+ 状态词统一。

### 验证
- 每步 `pnpm build` 通过（vite 构建含类型检查）。
- 3 秒测试 + 键盘可达 + 移动端 Drawer 全屏 + 骨架屏加载态。
- 用户管理/日志在 VOS 与独立部署下权限行为不变。

## 7. 明确不做（范围纪律）

- 不改后端 API，不新增字段，不动 `/profile`。
- 不把监控做成主页面主体（运行状态保持次要、只读）。

- 不显示「配置完成度百分比」数字（制造焦虑），用「下一步引导」替代。

## 8. 媒体库管理落地方式（待定，A/B/C）

> 媒体库管理 = 操作区（与文件管理同属「内容操作」），需从 admin library tab 移出。三种方式工程成本递增：

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 并入 /files** | 作为 /files 第 5 个 tab（libs） | 最"放一起"，与文件管理同页 | /files 已有 4 tab 会挤；LibraryManager 需接收文件管理页的 WebSocket/state |
| **B. 独立侧边栏入口** ⭐ | 新路由（如 /media-libs），与 /files 相邻 | 不挤 /files；操作区入口清晰 | 需迁移扫描进度 WebSocket 状态到新页 |
| **C. 物理不动** | LibraryManager 留 admin，导航分组叙事改为"内容操作" | 零迁移成本 | "放一起"只是概念，admin 仍含操作 |

**推荐 B**：侧边栏管理区变为「媒体库管理 / 文件管理 / 系统管理」三项，前两项相邻同属内容操作，admin 纯配置化。

**迁移注意**（B 或 A）：
- LibraryManager 依赖 AdminPage 的 `scanning / scanProgress / scrapeProgress / scanPhase` 状态 + localStorage 持久化 + WebSocket 事件 —— 整套迁到新宿主，逻辑不动。
- TMDb / 豆瓣配置留在 admin（元数据刮削 Drawer），不随 LibraryManager 迁移。
- ClassificationTab（归类规则）与扫描强相关，**跟随媒体库管理**迁移。
